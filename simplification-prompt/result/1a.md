## Recommendation: benchmark a capability frontier, not a fixed task

Create a private, renewable **“Ship the Release”** benchmark:

> Given an unfamiliar repository snapshot, a one-page product request, and normal agent tools, deliver a merge-ready release: implementation, tests, documentation, migration notes, and a runnable demonstration.

This is unusually well matched to your work: coding GenAI demos, evaluating agents, creating teaching infrastructure, and converting ambiguous ideas into working artifacts.

A fixed benchmark will eventually saturate or become contaminated. Recent evidence is stark: SWE-Bench Pro’s public split reportedly rose from 23.3% to 80.3% in eight months, while a subsequent audit estimated that roughly 30% of its tasks were broken. ([OpenAI][1]) Instead, measure how far up an expandable difficulty ladder an agent can reliably operate.

## The task ladder

Use tasks corresponding to increasing amounts of competent human work:

| Level | Approximate human effort | Example                                                    |
| ----- | -----------------------: | ---------------------------------------------------------- |
| 1     |            15–30 minutes | Diagnose and fix a bug                                     |
| 2     |                1–2 hours | Add a cross-file feature with tests                        |
| 3     |               Half a day | Feature, migration, documentation and demo                 |
| 4     |                 1–2 days | Implement a small release containing several changes       |
| 5     |             About a week | Build and validate a new subsystem or experimental product |

Measure:

**H80 = the longest human-sized task the agent completes successfully in 80% of runs.**

Also retain cost per successful task, elapsed time, number of human interventions, and perhaps H50. This follows the useful part of METR’s time-horizon approach: difficulty is expressed as expert human task duration rather than as an arbitrary collection of questions. METR fits success probability against human completion time and reports 50% and 80% horizons. ([Metr][2])

Use your own completion time—or that of someone familiar with your stack—for calibration. Generic contractors may take longer because they lack the context you normally have, a limitation METR also notes. ([Metr][2])

## Make evaluation almost mechanical

Each task should have:

* Public acceptance tests that establish the basic contract.
* Hidden behavioural and adversarial tests.
* The original regression suite.
* A script that launches the artifact and performs one end-to-end operation.
* A small human rubric only for qualities that cannot be tested automatically.

A possible score:

| Component                                 | Weight |
| ----------------------------------------- | -----: |
| Hidden functional tests                   |    40% |
| No regressions                            |    20% |
| End-to-end usability                      |    15% |
| Requirements coverage                     |    10% |
| Tests and verification added by agent     |    10% |
| Efficiency and minimal unnecessary change |     5% |

Make build failure, data corruption, fabricated results, or unsafe irreversible actions hard failures. Run each system three to five times; agent reliability is often more revealing than its best run.

Long-horizon benchmarks increasingly use partial-credit grading because binary pass/fail discards substantial information. Long-Horizon-Terminal-Bench, for example, decomposes tasks into graded subtasks; its strongest tested agent achieved only 10.9% perfect completion, leaving considerable headroom. ([arXiv][3])

## The best source of tasks: your real backlog

Before solving a real task yourself:

1. Freeze the repository and input artifacts.
2. Write acceptance criteria and hidden tests separately.
3. Estimate how long you expect the task to take.
4. Run the agents.
5. Later add your actual implementation or observed failure modes to the grader.

Good examples for you would be:

* Add a new capability to one of your GenAI demos, including deployment and documentation.
* Evolve a TDS autograder after a substantial assignment-specification change.
* Convert an exploratory notebook into a tested, reusable CLI or web application.
* Upgrade an internal LLM workflow while preserving old inputs and outputs.
* Reproduce several related changes described in release notes against an older repository snapshot.

The last format closely resembles SWE-EVO: agents receive release-level requirements rather than one isolated issue and must coordinate changes across many files. Its tasks average about 21 modified files and 874 tests; the best reported agent solved 25%, versus much higher performance on older isolated-issue benchmarks. ([arXiv][4])

Keep the tasks private until retirement. That reduces contamination and lets you use actual business, teaching, or unpublished project work.

## Add difficulty without changing the basic benchmark

Once models begin succeeding, increase one dimension at a time:

* More interacting requirements, not merely more lines of code.
* An underspecified requirement where the correct action is to ask a question.
* A requirement change delivered halfway through execution.
* A broken dependency, flaky service, or misleading error.
* Several source artifacts containing irrelevant or conflicting information.
* A requirement to independently verify outputs before declaring completion.
* A longer interval between repository versions.
* A fixed dollar, token, wall-clock, or experiment-compute budget.

These variations target current agent weaknesses rather than raw coding syntax. OSWorld 2.0 found that long workflows frequently fail because agents lose constraints, miss information arriving mid-task, guess instead of asking, or skip verification; its best reported binary completion was 20.6%. ([arXiv][5])

## Two additional task families

### 1. Autograder Duel

Give the agent a learning objective and starter repository. Require it to produce:

* The assignment.
* A reference implementation.
* An autograder.
* A collection of plausible incorrect and adversarial submissions.
* Student-facing feedback.

Evaluate it against a hidden corpus containing correct alternative solutions, common mistakes, malicious grader exploits, inefficient solutions, and formatting variations.

The objective metrics are excellent: false acceptance rate, false rejection rate, exploit survival rate, runtime and quality of feedback. This is probably your **easiest benchmark to evaluate** and directly improves your teaching infrastructure.

### 2. Reproduce and Improve

Give the agent a recent paper, repository, dataset and fixed compute budget. Require it to:

1. Reproduce one stated result.
2. Diagnose any discrepancy.
3. Implement one justified extension.
4. Improve a predefined held-out metric.
5. Package the entire result reproducibly.

Grade using metric thresholds, output hashes, clean-environment reruns, compute expenditure and whether the conclusions match the produced evidence.

This has the greatest long-term headroom, particularly when papers and tasks are selected after model training cutoffs. It is more expensive to run, but it tests research execution rather than research-flavoured prose. METR’s newer “expenditure horizon” work similarly argues that continuous performance and resource budgets reveal more than binary success alone. ([Metr][6])

## Benchmark the agent system, not only the model

Your primary leaderboard should compare the complete configuration:

`model + harness + tools + context strategy + retries + budget`

Then run a controlled model comparison by swapping only the model. Harness choice itself can materially alter results: WildClawBench reported shifts of up to 18 percentage points for the same model under different agent harnesses. ([arXiv][7])

A practical initial suite would be 12 private “Ship the Release” tasks—four around 30 minutes, four around two hours and four around one working day—plus five Autograder Duel tasks. The main number should be **H80**, accompanied by cost per success and human-intervention minutes. As systems improve, add longer tasks rather than replacing the measurement.
