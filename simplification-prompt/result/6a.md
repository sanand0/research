# LadderBench: a self-escalating benchmark for practical agents

No finite benchmark is literally unsaturable. The practical goal is narrower and achievable: make it impossible to win through memorizing instances, writing persuasive answers, or triggering shallow completion checks—and make genuine competence automatically expose harder tasks.

Existing work provides useful pieces: WebArena demonstrated reproducible, self-hosted functional environments; τ-bench scores actual database state and measures consistency across repeated attempts; METR estimates a capability frontier rather than averaging unrelated task scores; recent dynamic-evaluation work explores procedurally targeting difficulty. ([arXiv][1])

## 1. Core concept

Each episode creates a fresh, seeded **micro-organization** containing:

* An inbox
* Documents and spreadsheets
* A calendar
* A ticketing or CRM database
* A small ledger
* Optionally, a Git repository
* A deterministic virtual clock and simulated colleagues

The agent receives a goal such as:

> Resolve the Acme renewal before the deadline. Select an eligible vendor, avoid duplicate payment, schedule the required review, and leave an auditable decision record.

It receives tools, not direct database access. Its score depends on what changed in the environment—not on its final explanation.

An episode is formally:

[
E=(W_0,\ G,\ F,\ C,\ B,\ T)
]

where:

* (W_0): initial world state
* (G): required final-state predicates
* (F): forbidden states or actions
* (C): policy and consistency constraints
* (B): token, action and monetary budget
* (T): virtual deadline or event schedule

The main result is binary: all required predicates hold, no hard constraint is violated, and the budget is respected.

## 2. Generate tasks from solutions, not prompts

The generator should first construct a valid hidden **witness plan**, then produce the task.

1. Sample a dependency graph of facts and actions.
2. Populate a fresh world with synthetic entities and random values.
3. Execute a reference solver to prove that at least one valid solution exists.
4. Add distractors, stale information, exceptions and alternative paths.
5. Render the user request and tool documentation.
6. Keep the witness inaccessible to the tested agent.
7. Reveal it after the run for auditing.

This eliminates the common failure mode where generated tasks are ambiguous, impossible or incorrectly graded.

A dependency graph might require the agent to:

```text
Read renewal request
  ├─ Find current contract
  ├─ Check customer risk status
  └─ Collect vendor quotes
         ├─ Exclude expired quote
         └─ Apply regional procurement rule
                    ↓
             Select valid vendor
                    ↓
       Reserve reviewer availability
                    ↓
       Update CRM + ledger + audit note
```

Random prose alone does not create diversity. Randomized **causal structure** does.

## 3. Difficulty is multidimensional

Do not define difficulty merely as “more steps.” Give the generator independent knobs:

| Axis                | Easy               | Hard                                    |
| ------------------- | ------------------ | --------------------------------------- |
| Dependency depth    | One lookup         | Nested cross-source dependencies        |
| Branching           | One obvious option | Many plausible but invalid options      |
| Policy depth        | Direct rule        | Exceptions overriding exceptions        |
| Observability       | Facts colocated    | Facts scattered across tools            |
| Temporal dynamics   | Static world       | Expiring offers and incoming events     |
| Reversibility       | Editable draft     | Irreversible external action            |
| Tool reliability    | Always succeeds    | Timeouts, stale reads, safe retries     |
| Constraint coupling | Independent goals  | One action affects several goals        |
| Optimization        | Any valid solution | Minimize cost subject to constraints    |
| Schema novelty      | Familiar fields    | Fresh entity and field compositions     |
| Context pressure    | Little noise       | Relevant facts separated by distractors |
| Interaction         | No clarification   | Deterministic simulated-user dialogue   |

Most harder episodes should increase **constraint density**, not just token consumption. This keeps evaluation affordable while still differentiating stronger agents.

## 4. Automatic escalation

Represent every generated episode by a feature vector (x). Initially predict its difficulty using a simple model:

[
\hat{\beta}=w^\top x
]

After observing results across agents, calibrate empirical item difficulty using a one-parameter item-response model:

[
P(\text{pass}\mid\theta,\beta)=\sigma(\theta-\beta)
]

Here, (\theta) is agent capability and (\beta) is episode difficulty.

For each evaluated agent:

1. Begin with several common anchor episodes.
2. Estimate a posterior over (\theta).
3. Generate the next episode near the current uncertainty frontier.
4. After each result, update the posterior.
5. Stop when the confidence interval is sufficiently narrow or the run budget is exhausted.

Target episodes with predicted success rates around 35–65%. Easy tasks are useful only as anchors and regression checks; impossibly hard tasks provide little information.

The generator should also maintain a **failure archive**. For recurring failures, create controlled mutations:

* Change only the critical policy exception.
* Move one decisive fact to another tool.
* Introduce a safe-retry requirement.
* Add a conflicting but older record.
* Make an action irreversible.
* Require optimization rather than mere feasibility.

Retain mutations that discriminate among current systems. Retire them from the active frontier once nearly all systems pass—but preserve them as anchors.

## 5. Scoring that cannot be gamed by prose

Use one primary score and several transparent diagnostics.

### Primary: reliable difficulty frontier

Report:

* **Frontier-50:** difficulty at which estimated success is 50%.
* **Frontier-80:** difficulty at which estimated success is 80%.

Under the logistic model:

[
\text{Frontier}_{80}=\theta-\operatorname{logit}(0.8)
=\theta-1.386
]

Frontier-80 is the better headline score because useful agents need consistency, not occasional success. τ-bench similarly motivates evaluating repeated-run reliability rather than relying only on pass-at-one. ([arXiv][2])

### Keep these separate

Do not hide everything inside a composite number. Also report:

* Hard-constraint violation rate
* Success per 1,000 model tokens
* Median tool calls per successful episode
* Retry and recovery success
* Counterfactual sensitivity
* Success across three independent repeats on a small reliability slice

A severe forbidden action should make the episode fail, not merely subtract a few points.

The agent’s final prose should either be ignored or capped at roughly 300 characters. It may be stored for inspection, but it must not affect the core score.

## 6. Deterministic verification

The verifier should have three layers.

### Final-state predicates

Examples:

```sql
SELECT vendor_id FROM renewals WHERE account_id = :account
    = :optimal_eligible_vendor

SELECT COUNT(*) FROM payments
WHERE invoice_id = :invoice
    = 1
```

### Invariants

Examples:

* No message was sent before approval.
* No customer marked “do not contact” was contacted.
* No ledger transaction was duplicated.
* Every external action has an internal audit record.
* The chosen option was eligible at the time of action.
* No action occurred after its deadline.

### Trace-derived checks

Because the agent can interact only through instrumented APIs, the evaluator can verify:

* Which state transition each action caused
* Whether retries were idempotent
* Whether the agent observed an updated record before acting
* Whether an irreversible action followed the required approval
* Whether success came from legitimate tools rather than evaluator access

The core verifier should contain no LLM judge. LLM-based critique may be added as a diagnostic, never as the source of the pass/fail result. Final-state-only evaluation is attractive but can miss unusable or poor-quality intermediate work; current research has also emphasized richer trajectory and provenance auditing. ([arXiv][3])

## 7. Counterfactual twins defeat scripted completion

For a subset of episodes, generate two worlds differing in exactly one decisive fact:

* Vendor A is eligible in one world and prohibited in the other.
* A quote expires before the deadline in only one world.
* The customer consents to contact in one world but not the other.
* A calendar slot is available in only one world.

The correct action must change.

Score the pair jointly:

```text
Twin pass = both episodes pass
            AND the decisive action differs appropriately
```

This detects:

* Memorized action sequences
* Generic “always choose the cheapest” policies
* Agents that ignore tool results
* Systems that accidentally reach the correct state
* Superficial strategies that exploit common task templates

Use perhaps 10–20% of the run budget for twins; they are disproportionately diagnostic.

## 8. Contamination resistance

Use public generators and verifiers but private per-run seeds.

Before evaluation:

```text
run_secret = random 256-bit value
commitment = SHA256(run_secret)
publish(commitment)
```

Derive each episode deterministically:

```text
episode_seed =
    HMAC(run_secret, model_id || run_id || episode_index)
```

After evaluation, reveal `run_secret`. Anyone can then regenerate every task and verify that episodes were not selected after seeing the results.

Additional protections:

* Generate all names, amounts, dates, identifiers and causal relations at runtime.
* Use a combinatorial task grammar, not a finite prompt bank.
* Never publish active evaluation seeds before a run.
* Periodically add new operator combinations rather than only new wording.
* Randomly assign semantically equivalent interface representations.
* Include counterfactual twins and hidden random dependencies.
* Separate the agent container from the world server and verifier.

Recent analysis of static software-agent benchmarks illustrates why instance overlap and benchmark familiarity can become serious validity concerns. ([arXiv][4])

A model may eventually learn the general generator structure. That is acceptable: mastering the underlying operations and policies is genuine transferable competence. It still cannot memorize the unknown world state.

## 9. Preserve longitudinal comparability

Purely adaptive benchmarks risk becoming moving targets. Use three pools:

* **Anchors:** stable, encrypted seeds shared across evaluation runs.
* **Frontier:** freshly generated episodes near current capability.
* **Probes:** new task operators and counterfactual mutations.

A practical allocation is:

```text
25% anchors
50% adaptive frontier
15% reliability repeats
10% counterfactual twins
```

Calibrate every new task against anchor performance. Store generator version and feature vector with each episode. When the generator changes substantially, overlap old and new versions for several runs to estimate a linking transformation.

Report the capability scale, generator version and confidence interval—not only a raw percentage.

## 10. Keep model and scaffold comparisons separate

Provide two tracks.

**Fixed-harness track:** Every model uses the same minimal agent loop, system prompt, tool descriptions, context policy and action budget. This primarily compares models.

**Open-system track:** Entrants may change prompting, planning, memory, orchestration and retry policies, but face the same world and resource accounting. This compares deployable agent systems.

Never place results from the two tracks in one ranking.

## 11. A cheap standard run

Use sequential stopping instead of a fixed enormous suite.

A reasonable configuration:

```yaml
minimum_episodes: 16
target_episodes: 32
maximum_episodes: 48

max_tool_calls_per_episode: 20
max_irreversible_actions: 3
virtual_time_limit: 2_days
target_capability_ci_width: 0.50
```

The environment and verifier run locally, so evaluator cost is negligible. Model inference is the main expense. A 16-episode smoke test can catch regressions; 32–48 adaptive episodes provide a more credible comparison without running hundreds of mostly uninformative tasks.

The run should stop early when:

* The capability interval is sufficiently narrow.
* The agent clearly falls below the initial ladder.
* It repeatedly violates a critical constraint.
* It reaches the current generator ceiling, triggering generation at a higher range.

## 12. Audit artifact for every episode

Emit a self-contained bundle:

```text
manifest.json
task.json
initial_state.sqlite
tool_docs/
trace.jsonl
model_messages.jsonl
state_deltas.jsonl
final_state.sqlite
verdict.json
resource_usage.json
witness.json          # released only after execution
replay.sh
```

`verdict.json` should explain every predicate mechanically:

```json
{
  "passed": false,
  "required": {
    "correct_vendor": true,
    "meeting_scheduled": true,
    "audit_record_created": false
  },
  "forbidden": {
    "premature_external_message": false,
    "duplicate_payment": false
  },
  "budget": {
    "tool_calls": 14,
    "limit": 20
  }
}
```

This makes every failure inspectable without trusting a leaderboard operator.

## 13. Minimum viable version

Start with four tools:

* Inbox
* Files
* Calendar
* CRM/ledger

Implement twelve task operators:

```text
lookup
cross-source join
filter
rank
apply rule
apply exception
schedule
update
send
approve
retry safely
record provenance
```

Build tasks by composing three to eight operators. Add virtual-time events, optimization and Git only after the basic evaluator is stable.

The reference solver can be deliberately ordinary: graph search over structured state, not another frontier model. Any task it cannot solve deterministically should be rejected during generation.

## 14. The benchmark’s central rule

**Never ask whether the agent appears to have completed the task. Ask whether the world is now correct, safe, efficient and causally responsive to the facts it encountered.**

That produces a benchmark whose frontier moves with capability, whose instances cannot be memorized in advance, whose main score ignores verbosity, and whose decisions remain locally reproducible and auditable.
