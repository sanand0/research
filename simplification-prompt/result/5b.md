## Conclusion

The most likely wrong belief is this:

**A higher average task-success score gives a portable measure of agent quality.**

Portable means that the agent rank stays valid after changes to tools, infrastructure, users, and human control.

The score usually measures one complete workflow, not an agent alone. A workflow includes the model, harness, tools, infrastructure, user, and human handoff rule.

A harness is the software that supplies tools and controls model actions.

## Evidence of acceptance

Researchers describe mean task success as the dominant agent evaluation method. Anthropic reports that small leaderboard differences increasingly influence deployment decisions.

A 2026 production study surveyed 86 practitioners and completed 20 case studies. Seventy-four percent mainly used human evaluation. Reliability remained their main development problem. ([arXiv][1])

Thus, the belief is often implicit. Companies act as if one evaluation rank can support a deployment choice.

## Primary evidence against the belief

First, infrastructure can change the score.

Anthropic kept the model, harness, and tasks constant in a Terminal-Bench experiment. Resource settings changed success by six percentage points. This difference exceeded many gaps between leading models. ([Anthropic][2])

Second, accuracy can improve without similar reliability improvement.

Princeton researchers tested 15 models on two agent benchmarks. Across 24 months, accuracy gains were much larger than reliability gains. More accurate agents still changed across runs and prompt wording. They also poorly predicted their own success. ([arXiv][3])

Third, the human-agent policy changes the evaluated system.

The production study found that 68 percent of agents needed human action within ten steps. Therefore, the human handoff rule is part of the system. ([arXiv][1])

Fourth, direct work outcomes can disagree with perceived agent quality.

METR randomized 246 real issues across 16 experienced open-source developers. Early-2025 AI tools increased completion time by 19 percent. Developers still estimated a 20 percent speed increase. ([METR][4])

METR later said that newer tools probably gave more speed improvement. However, participant selection prevented a reliable new estimate. ([METR][5])

These results do not show that task-success scores are useless. They show that a score can fail when the operating condition changes.

Use task success as a diagnostic measure. Do not use it as the final deployment objective.

Use expected production loss for the final rank:

**Production loss = correction cost + run cost + delay cost + failure cost + missed-value cost.**

Failure cost must include both frequency and severity.

## Strongest innocent alternative

Companies can use task success only as an early filter. They can then use human review, small live tests, and monitoring.

This method is valid when four conditions are true:

1. Test cases have the same distribution as production cases.
2. Tools, resource limits, and handoff rules are the same.
3. The score gives larger penalties to more costly errors.
4. Repeated trials show stable behavior.

When these conditions hold, one score can predict production loss.

The evidence does not show that no company meets these conditions. It shows that teams must test score transfer instead of assuming it.

The evidence also has limits. The reliability study used two benchmarks. The production survey was not a census. The METR trial covered one developer group and one tool period.

Therefore, this conclusion is a strong default hypothesis, not a universal rule.

## Cheapest decisive test

Use a blind, paired shadow replay.

Shadow replay means that agents use copied cases and cannot change live systems.

1. Select the current score winner, A, and the nearest runner-up, B.
2. Randomly order 200 recent production cases.
3. Start with the first 30 cases.
4. Replay each case with A and B in the exact production harness.
5. Run each agent three times per case.
6. Block all writes to live systems.
7. Hide the agent name from reviewers.
8. Mark agreement only when outputs, final states, and tool side effects match.
9. Review only disagreements, unstable runs, and safety-rule events.
10. Measure production loss for each run.
11. Add cases in blocks of 20 when the result remains uncertain.

Before the test, set δ as the minimum useful loss reduction.

Define D as the production loss of A minus the production loss of B. Use a paired confidence sequence for D.

My conclusion is false for this workflow when all three conditions occur:

* The upper limit for D is below −δ.
* A has no additional severe failures.
* A has equal or better repeat consistency.

This design needs no new benchmark and no live customer exposure. It uses existing logs and reviews only informative cases.

The broad conclusion fails if the offline winner passes this test across several independent workflows without a rank reversal.
