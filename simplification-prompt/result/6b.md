# RatchetBench

Use a deterministic local work environment. Generate each task from a new private seed. Score only tool actions and the final environment state.

No benchmark can prevent all benchmark-specific training. This design makes instance memorization, long answers, and false completion insufficient. ([OpenReview][1])

## 1. Build one local work environment

Use one Python process with SQLite and JSON files.

Give the agent tools for mail, files, tables, calendars, tickets, and simple service APIs.

Do not use the internet. Do not use a model judge. Make each tool deterministic.

Use a small task language with templates and constraints. Do not use a model to create scored tasks.

Each task contains these items:

* An initial state.
* A user request.
* Goal predicates.
* State invariants.
* Forbidden events.
* A tool-call limit.
* A token limit.
* A deterministic test suite.

A solver must verify that each generated task has at least one valid solution.

## 2. Test real agent work

Each task must cause a state change. A text claim does not complete a task.

Use six task families:

1. Find and reconcile records.
2. Plan and complete a transaction.
3. Obey several dependent constraints.
4. Recover from a tool fault.
5. Adapt to a goal change.
6. Reject conflicting or unsafe instructions.

For some tasks, require a report. Require a strict JSON schema for that report.

Do not give points for explanations. Set a small final-answer limit.

Example task:

> Move order O17 to the earliest slot with capacity. Notify the purchaser. Do not expose the internal risk note.

The tests check the new date, remaining capacity, message recipient, ticket status, and unchanged risk note.

## 3. Control difficulty with clear parameters

Give each task a difficulty vector:

* H: minimum necessary tool calls.
* B: number of plausible decoys.
* C: number of linked constraints.
* P: amount of hidden state.
* F: number of recoverable tool faults.
* G: number of goal changes.
* T: number of tools that the agent must combine.

Increase these values to create harder tasks. Keep the task grammar and the scorer unchanged.

ACE-Bench uses scalable horizons and decoy budgets in a lightweight environment. This result supports these two difficulty controls. ([arXiv][2])

## 4. Add a hardness miner

Run the hardness miner only when the best agents pass the highest active band.

The miner does this procedure:

1. Mutate tasks above the current band.
2. Reject tasks that the solver cannot complete.
3. Reject ambiguous tasks.
4. Test a small sample with three strong agents.
5. Keep tasks with pass rates from 30 percent to 70 percent.
6. Link the new band to old bands with anchor tasks.

Activate the new band after two consecutive saturation results. Use an 80 percent pass rate as the saturation limit.

This process gives the benchmark no fixed maximum level.

## 5. Use an adaptive test

Start each run with ten fixed anchor tasks. Use them to keep scores comparable across benchmark versions.

Fit a one-parameter Item Response Theory model. Estimate the agent ability from the anchor results.

Then, select tasks near the estimated ability. Choose tasks with a predicted pass chance from 40 percent to 60 percent.

Use ten anchors, 20 adaptive tasks, and ten confirmation tasks.

Put the confirmation tasks one band below the estimated capability. Use them to measure reliability.

A recent study found that medium-difficulty tasks preserved rankings with fewer evaluations. It reduced task counts by 44 percent to 70 percent. ([arXiv][3])

## 6. Score verified capability

A task passes only when all goal predicates are true.

The task also requires all invariants, no forbidden event, and completion within the resource limits.

Publish four results:

* Capability: the difficulty with a predicted 50 percent pass rate.
* Reliability: the pass rate one band below capability.
* Efficiency: the median tool calls and tokens for successful tasks.
* Violation rate: the rate of forbidden actions and broken invariants.

Do not combine these results into one weighted total.

Use capability as the primary rank. Require 90 percent reliability and zero severe violations.

Use efficiency only to resolve equal ranks.

A long answer cannot increase the score. A false claim cannot change the environment state.

## 7. Prevent simple memorization

Generate all names, values, dates, links, and record structures after model submission.

Use new seeds for each run. Keep each seed secret until the run ends.

Publish a seed hash before the run. Publish the seed after the run.

For a public leaderboard, derive seeds from a future public random value.

Release all old tasks, seeds, traces, and tests. Keep only the next task set private.

Hold out new task compositions, not only new task values.

Keep 20 percent of composition operators private for one round. Release them after that round.

Add a counterfactual twin to one task in four. Change one important fact in the twin.

The correct action must change with that fact. This test detects fixed plans and shallow pattern use.

Dynamic task generation reduces instance contamination. It does not prevent training on the test task itself. Composition holdouts reduce this risk. ([OpenReview][4])

## 8. Make every result auditable

Save one run directory with these files:

* The code commit.
* The model and agent configuration.
* The prompt and tool schemas.
* The seed hash and revealed seed.
* Every tool call and tool result.
* Every state change.
* Every test result.
* The final score.

Provide an audit program. It must replay the trace and reproduce the score without model calls.

Sign the manifest with a SHA-256 hash. Make all benchmark versions permanent.

## 9. Keep the run cheap

Run all tools in memory or in local files.

Use exact program tests. Do not pay for human review or model review.

Limit each task to 12 tool calls. Limit each run to 40 tasks.

Select mostly medium-difficulty tasks. Do not spend calls on tasks that all agents pass or fail.

The model inference cost is the main variable cost. The benchmark environment adds almost no variable cost.

## Minimum useful version

Start with one environment, six task families, 24 base templates, and eight difficulty bands.

Run ten anchors, 20 adaptive tasks, and ten confirmation tasks for each agent.

After each public round, release the complete audit package.

**Score verified state change under constraints. Increase generated complexity when frontier agents reach the current limit.**
