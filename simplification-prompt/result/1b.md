## Recommendation

Use a **private, rolling “request-to-working-tool” benchmark**.

Give the agent a new business request, an unfamiliar repository, data, and tool documentation.

Require the agent to produce these items:

1. Working code.
2. Automated tests.
3. A small demonstration.
4. A short README.
5. Evidence that the result meets each requirement.

This task matches your normal work. It tests coding, research, tool use, planning, debugging, and verification.

Terminal-Bench uses similar realistic tasks with executable tests. Current frontier agents still score below 65 percent. ([arXiv][1])

## Three task types

### 1. Request to micro-product

Example:

> Add semantic search to this unknown repository.
> Use the supplied documents and API.
> Add tests, logging, caching, and a command-line interface.

Use hidden tests to check the result.

Change the repository, data, API, and requirements for each evaluation.

This must be your main benchmark.

### 2. New paper to working demonstration

Give the agent a recent paper and a small data set.

Ask it to:

1. Find the main method.
2. Implement a useful part.
3. Compare it with a baseline.
4. Create a working demonstration.
5. Report unsupported claims.

Check numerical results, tests, citations, and demonstration behavior.

This task measures research and implementation as one workflow.

### 3. Workplace state-change task

Create a simulated system with messages, files, calendars, policies, and tools.

Example:

> Review the project messages.
> Find the delayed deliverable.
> Update the plan.
> Schedule the correct people.
> Do not disclose restricted information.

Check the final database state.

This method gives simple and objective evaluation. τ-bench also compares the final database state with the required state. It uses repeated trials to measure reliability. ([arXiv][2])

## Prevent saturation

Do not keep one fixed task set.

Generate new tasks from your real backlog each month. Keep the tasks private until the test is complete.

Use these difficulty controls:

* Increase the number of tools.
* Add incomplete or conflicting information.
* Change data formats and API versions.
* Add delayed information during execution.
* Add recoverable tool failures.
* Add requirements that need a user question.
* Increase the work horizon.
* Use unfamiliar repositories.

Long workflows remain difficult. OSWorld 2.0 tasks use an average of 318 tool calls. The best tested agent completed only 20.6 percent. Common failures included missed constraints, poor questions, and weak verification. ([arXiv][3])

Dynamic environments also reduce contamination and saturation. Agent Island uses changing opponents instead of a fixed task set. ([arXiv][4])

## Score

Use this score:

[
\text{Score} =
\text{task success}
\times
\text{reliability}
\times
\text{efficiency}
]

Measure these values:

* Hidden-test pass rate.
* Final-state correctness.
* Success in five independent runs.
* Human intervention count.
* Cost.
* Time.
* Unsupported claim count.
* Unnecessary file or state changes.

Keep task success as a gate. A fast incorrect result must score zero.

Do not use an LLM judge as the main evaluator. Use tests, database checks, and artifact checks. Poor reward design can produce large errors in agent benchmark results. ([arXiv][5])

## Best single benchmark for you

Use this task:

> Convert a fresh, imperfect business or research request into a tested, useful, and documented LLM micro-product.

Create ten new instances for each important model release.

This benchmark will measure capability that you use. It will also grow with the models.
