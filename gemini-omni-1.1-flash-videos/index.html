Gemini Omni 1.1 Flash: I tried the controls

Google released Gemini Omni 1.1 Flash on 27 Aug 2026. I was less interested in whether it could make another beautiful 8-second video. We had already tried that sort of thing. The annoying problems were: can I fix one mistake without changing five other things? Can a person survive past 10 seconds? Can I tell a shot where to end? Can a video itself specify motion?

So I tested those four things. The videos below are the tests, not illustrations of the tests. I kept the prompts, API parameters, usage, failures, and even the experiments I threw away.

Source: github.com/sanand0/research/gemini-omni-1.1-flash-videos. Google references: launch post, Omni guide, pricing, release notes, Python SDK.

Omni 1.1 makes video more controllable

Google's API guide now documents stateful editing, extension, first/last-frame interpolation, and image/video references in one model. Those map unusually well to the problems we had hit in earlier video-generation work. Short clips were already easy. Changing and continuing them was the expensive bit.

EXPERIMENT 01

It can change one thing without remaking the shot

I made a shop scene with an orange payment terminal, then gave it one edit: change only the terminal to cobalt blue; keep everything else the same.

Result

The 720p result is almost frame-identical outside the edit. SSIM is 0.986, with substantial change concentrated around the terminal.

Watch for

360p edit fidelity did not predict 720p. The same edit at 360p had SSIM 0.70 and changed much more. Cheap drafts are useful for searching ideas, but I would not use them to judge surgical edit quality.

Exact prompts
BASE
Exactly 8 seconds. Single continuous locked-off shot, no cuts.

A small-business owner in a cobalt-blue apron stands behind a modern neighbourhood shop counter. An ORANGE payment terminal is clearly visible on the counter. A red ceramic mug sits to the left and a green plant to the right.

She scans one parcel, taps the orange terminal once, puts a receipt into a paper bag, then smiles.

Natural shop ambience. No dialogue. No music. No text overlays.

EDIT
Change only the orange payment terminal to cobalt blue. Keep everything else the same.
API parameters and run
model = "gemini-omni-1.1-flash"
response_format = {
  "type": "video",
  "aspect_ratio": "16:9",
  "resolution": "360p" or "720p",
  "duration": "8s",
  "delivery": "uri"
}

Explore: 3 independent 360p base videos; edit candidate 1.
Final: fresh 720p base; edit with previous_interaction_id=base.id.

Cost: $2.84 in usage-backed calls, plus about $0.82 for an accidental duplicate 720p base generation caused by a logging BrokenPipe after the API call had already succeeded. I fixed the resume/logging bug afterwards.

EXPERIMENT 02

It can extend a 10-second scene to 30 seconds

Result

The final output is 30.016 seconds. The person, face, voice, jacket, room, mug, terminal, camera, and lighting stay remarkably stable across both extensions.

Watch for

Leave about two seconds of silence around an extension join if speech matters. My first draft put speech across the 20-second boundary. The model rewrote the tail and created an audible false start. Google's prompt guide says final input frames may be edited to make an extension seamless. Moving speech away from the join fixed it.

Exact prompts
TURN 1
Exactly 10 seconds. Single continuous locked-off medium shot, no cuts. A woman in a distinctive cobalt-blue jacket stands behind a small-business counter. A red ceramic mug is on her left and a blue payment terminal on her right. Warm morning light. In the first six seconds, she says in a crisp calm Indian-English voice: 'Ten seconds used to be the wall. Continuing meant starting over.' Then she stays silent for the rest of the shot and slowly picks up the red mug. No music. Natural room ambience.

TURN 2
Continue the same unbroken scene for exactly 10 more seconds. Preserve exactly the same woman, voice, clothing, room, camera, lighting and ambience. In the first six seconds of this extension, she sets the mug down and says: 'Same face. Same voice. Same room. This is the second ten seconds.' Then she stays silent for the rest of this extension. No music.

TURN 3
Continue the same unbroken scene for exactly 10 more seconds. Preserve exactly the same woman, voice, clothing, room, camera, lighting and ambience. In the first six seconds of this extension, she says: 'Thirty seconds. One continuous story, not three unrelated clips.' Then she stays silent and smiles naturally until the end. No music.
API parameters and run
model = "gemini-omni-1.1-flash"
response_format = {
  "type": "video", "aspect_ratio": "16:9",
  "resolution": "720p", "duration": "10s", "delivery": "uri"
}

Turn 1: normal generation.
Turn 2: previous_interaction_id=turn1.id
Turn 3: previous_interaction_id=turn2.id

I first tried explicit video task="extend" together with previous_interaction_id.
The API rejected that combination with HTTP 400, so the working version relies on prompting, which Google recommends trying first.

Cost: $1.09 for the useful-but-bad 360p draft + $3.23 for the clean 720p final = $4.32. The rejected HTTP 400 returned no usage; I count it as $0.

EXPERIMENT 03

It can aim for a specific final frame

I took one frame from Experiment 1 and made two overlapping crops locally. No image model was involved. I passed those as <FIRST_FRAME> and <LAST_FRAME>.

Result

The generated first frame matches my supplied first frame at SSIM 0.974; the last matches at 0.973. The eight seconds in between are invented.

Watch for

This test used compatible endpoints from the same scene. It shows strong endpoint control, not that arbitrary first and last images will interpolate plausibly.

Exact prompt and API parameters
[# Sources <FIRST_FRAME>@Image1 <LAST_FRAME>@Image2]
Smooth cinematic camera move from the supplied first frame to the supplied last frame. Preserve the exact woman, cobalt-blue apron, payment terminal, red mug, counter, plants, shop layout and warm lighting. The camera smoothly moves from the left-hand viewpoint to the right-hand viewpoint with natural parallax. Single continuous shot, constant smooth camera speed, no jump cuts. Subtle shop ambience. No dialogue. Use Image1 as the exact starting frame and Image2 as the exact final frame.

model = "gemini-omni-1.1-flash"
input = [first-image, last-image, prompt]
response_format = {
  "type": "video", "aspect_ratio": "16:9",
  "resolution": "360p" or "720p", "duration": "8s", "delivery": "uri"
}

3 x 360p candidates + 1 x 720p final.

Cost: $1.67. This is the cleanest capability of the four for me because the endpoint is objectively testable.

EXPERIMENT 04

It can use another video as a motion reference

This one fooled me once.

Bad test

Do not describe the same motion in the text prompt if you are testing video-reference motion. My first prompt did that. The output looked good, but I could not tell whether the motion came from the video or my words. I threw away all four generations. They cost $1.70.

Then I removed the choreography completely. The text only says to copy the unusual sequence of poses from <VIDEO_REF_0>. The left side of the proof is the 3-second reference slowed to the same eight-second timeline; the right is the new scene. Google currently allows up to three video references of up to three seconds each and ignores reference-video audio.

Clean prompt and API parameters
[# References <VIDEO_REF_0>@Video1]
Copy only the body movement from <VIDEO_REF_0>. A faceless cobalt-blue training mannequin on a brightly lit football pitch performs the same unusual sequence of full-body poses, in the same order and with the same relative timing as the reference. Reproduce the motion faithfully; do not simplify it into a generic wave or exercise. Full body visible throughout. Fixed camera. Single continuous shot. No cuts. Do not copy the reference figure's appearance, colors, text or background. No dialogue. Use Video1 as a movement reference, not as a source for video editing.

model = "gemini-omni-1.1-flash"
input = [uploaded-3s-video-reference, prompt]
response_format = {
  "type": "video", "aspect_ratio": "16:9",
  "resolution": "360p" or "720p", "duration": "8s", "delivery": "uri"
}

3 x 360p candidates + 1 x 720p rerun.
Result

The clean run cost $1.70. Candidate 1 transfers the motion clearly enough for me even though the text never describes the choreography.

Watch for

A 720p rerun is a new stochastic generation, not the 360p winner at higher resolution. Candidates 2 and 3 were weaker, and the 720p rerun was weaker too. With no seed/replay control here, I would generate several finals or keep the best draft and upscale it. Also, reference-video audio is ignored.

The controls work, with a few important gotchas

Useful

Surgical editing is the biggest workflow change for me. Generating a plausible clip was already possible. Changing one thing without destroying the rest was the problem.

Gotcha

Keep speech about two seconds away from extension joins. The model may rewrite the tail of the previous clip. My first run turned that into an audible false start.

Useful

First + last frame is the most testable control. I can specify two images, measure both endpoints, and immediately see whether the model did what I asked.

Gotcha

Reference motion is not deterministic choreography replay. It worked, but adherence varied substantially across generations.

Google's 360p mode is useful for exploration. In my simple text-to-video calls it was roughly $0.035/generated second, close to the one-third-of-720p story. But the phrase "rerun the winner at 720p" is misleading when the winner depends on stochastic details. There is no winner to rerun unless the API gives me reproducible generation.

I had planned a fifth experiment called "Fail cheaply": generate six cheap drafts and finish one. I have not run it yet. After Experiment 4, I would change the question slightly: how often does a cheap draft predict what I will get in an expensive final?

The experiments are reproducible and resumable

The scripts use the official google-genai Python SDK, run as standalone uv scripts, and store an interaction ID, token usage, cost estimate, prompt, and output for each completed step. They resume from the last completed MP4+JSON checkpoint.

just build only invokes an experiment if its proof MP4 is missing, and only recompresses a WebM if the source MP4 is newer. On a fresh clone that means API calls and real spend. Published outputs are the specific stochastic runs described on this page.

I compressed the four proof videos using NVIDIA AV1 + Opus:

ffmpeg -i input.mp4 -c:v av1_nvenc -preset p6 -tune uhq -rc vbr -cq 55 -b:v 0 -spatial-aq 1 -temporal-aq 1 -c:a libopus -b:a 24k -vbr on -compression_level 10 output.webm
